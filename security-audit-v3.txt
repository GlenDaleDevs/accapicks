Security Audit V3 — Adversarial User Testing
==============================================
Date: 2026-02-08
Status: Post v2-fix re-audit. No critical/high issues found.

=== AUTH (9 findings) ===

[W1] Shared verification_code column
  Severity: Warning
  Detail: Same column used for email verification and password reset. If user requests
  password reset while mid-verification, the verification code gets overwritten.
  Impact: Minor UX annoyance, not exploitable.

[W2] Change-password: no brute-force protection
  Severity: Warning
  Detail: /auth/change-password doesn't increment failed_login_attempts on wrong
  current password. Attacker with stolen JWT could brute-force the current password.
  Impact: Low — requires valid JWT first.

[W3] is_active flag unused
  Severity: Warning
  Detail: User model has is_active column but it's never checked during login or
  any protected endpoint. A "deactivated" user can still log in and use the app.
  Impact: No current feature depends on this, but it's dead code.

[W4] No token invalidation on logout/password change
  Severity: Warning
  Detail: JWTs remain valid after logout or password change until they expire (30 min).
  Impact: Known JWT limitation. Would need token blacklist or short expiry to fix.

[S5] Login leaks verification status
  Severity: Suggestion
  Detail: Login returns different error for unverified ("Please verify your email")
  vs wrong password ("Invalid credentials"). Could confirm account existence.
  Impact: Minimal — signup already reveals if email is taken.

[W6] Email send failure swallowed
  Severity: Warning
  Detail: If Resend API fails, the error is caught and logged but user gets a success
  response. They wait for an email that never comes.
  Impact: UX issue, not security.

[S7] Verification code accepts non-digits
  Severity: Suggestion
  Detail: Code comparison is string-based, so "00123a" would just fail. But the
  frontend sends whatever the user types — no digit-only enforcement.
  Impact: Negligible.

[W8] Forgot-password can cycle verification_attempts
  Severity: Warning
  Detail: forgot-password generates new code but doesn't reset verification_attempts.
  However, repeated forgot-password calls generate new codes each time, effectively
  giving unlimited "fresh" codes to guess against.
  Impact: Low — rate limiter on the endpoint mitigates this.

[S9] Resend-code: no lockout check
  Severity: Suggestion
  Detail: resend-code doesn't check locked_until. A locked-out user can still
  trigger emails (but can't verify due to attempt limit).
  Impact: Negligible — just wastes email sends.

=== GROUPS (10 findings) ===

[W10] Non-atomic group creation
  Severity: Warning
  Detail: create_group does INSERT group then INSERT member in sequence. If the
  member INSERT fails, an orphaned group exists with no admin.
  Impact: Very unlikely failure case.

[W11] Invite code brute-force
  Severity: Warning
  Detail: 6-char alphanumeric = 2.1B combinations. join_group is rate-limited but
  a determined attacker could try codes. No per-IP or per-user attempt tracking.
  Impact: Low — rate limiter makes this impractical.

[W12] Invite code case sensitivity mismatch
  Severity: Warning
  Detail: Frontend uppercases invite codes, backend compares as-is. If codes are
  generated lowercase, the uppercase frontend version won't match.
  Impact: Codes are generated uppercase, so this is fine in practice.

[S13] No path parameter validation
  Severity: Suggestion
  Detail: groupId and accaId URL params aren't validated as integers before DB query.
  SQLAlchemy handles non-integer gracefully (returns None), but wastes a query.
  Impact: Negligible.

[W14] No onDelete CASCADE on foreign keys
  Severity: Warning
  Detail: Deleting a user or group doesn't cascade to related rows (bets, members,
  accas). Deletion is handled manually in application code.
  Impact: Data cleanup relies on app logic rather than DB constraints.

[W15] Admin role inherited on acca settlement
  Severity: Warning
  Detail: Only group admins can settle accas. If the admin leaves, no one can settle.
  Impact: Group becomes stuck. Would need admin transfer or multi-admin support.

[W16] Unsettleable accas if non-admin creator removed
  Severity: Warning
  Detail: If a non-admin member is removed, their bets are deleted. But only the
  admin can settle. If admin is removed via a different path, accas can't settle.
  Impact: Same as W15 — admin departure breaks settlement.

[W17] locks_at not recalculated on member removal
  Severity: Warning
  Detail: When a member is removed (admin kicks), their bets are deleted but
  locks_at isn't recalculated. The acca may lock based on a match that's no longer
  in any remaining bet.
  Impact: Acca locks earlier than needed. Not exploitable, just inaccurate.

[W18] locks_at not recalculated on leave_group
  Severity: Warning
  Detail: Same as W17 but when a user voluntarily leaves.
  Impact: Same — premature lock, not exploitable.

[S19] compare_bookmakers makes live API calls
  Severity: Suggestion
  Detail: Each compare_bookmakers request hits The-Odds-API (cached 30 min).
  Multiple users viewing same acca within cache window is fine, but cache misses
  burn API quota.
  Impact: Cost concern, not security.

=== BETS/ODDS (10 findings) ===

[W20] Fake event_id/teams not validated against API
  Severity: Warning
  Detail: Users can submit arbitrary event_id, home_team, away_team values.
  The backend doesn't verify these exist in The-Odds-API data.
  Impact: Users could create fake bets with made-up matches. Group trust model
  mitigates this (you're betting with friends).

[W21] Sub-1.0 odds allowed
  Severity: Warning
  Detail: Schema validates odds > 0, but real betting odds are always >= 1.0.
  Odds of 0.5 would halve the accumulator unfairly.
  Impact: Users could grief their group with absurd odds.

[W22] Zero-bet accas stuck forever
  Severity: Warning
  Detail: If an acca locks with 0 bets (everyone deleted theirs before lock),
  it can never be settled because there's nothing to settle.
  Impact: Clutters the group. Admin could potentially need a "delete acca" feature.

[S23] Same match picked across multiple accas
  Severity: Suggestion
  Detail: A user can pick the same match in different accas. Not necessarily a bug
  but could be restricted if desired.
  Impact: By design — accas are independent.

[W24] compare_bookmakers API quota burn
  Severity: Warning
  Detail: Same as S19 — repeated calls to odds API. The 30-min cache helps but
  doesn't eliminate quota usage for new match lookups.
  Impact: Cost concern.

[W25] Settlement team name mismatch
  Severity: Warning
  Detail: Auto-settlement compares team names from The-Odds-API scores endpoint
  against stored bet data. If API returns slightly different team names (e.g.,
  "Man Utd" vs "Manchester United"), settlement may fail silently.
  Impact: Could leave bets unsettled. Manual settlement via admin works around this.

[W26] locks_at can be pushed forward
  Severity: Warning
  Detail: If a user deletes their bet (the one with the earliest commence_time),
  locks_at is recalculated to a later time based on remaining bets. This extends
  the window for all users to modify picks.
  Impact: Group trust model — users extending lock time affects everyone equally.

[W27] Bet league not checked against acca leagues
  Severity: Warning
  Detail: An acca may be configured for "EPL only" but the backend doesn't enforce
  that bets must come from the specified leagues. The frontend filters available
  matches, but the API accepts any valid bet.
  Impact: Users could bypass league restrictions via API calls.

[S28] Custom bets bypass validation
  Severity: Suggestion
  Detail: Custom/manual bets skip all match validation (no event_id required).
  They also can't be auto-settled since there's no API match to check against.
  Impact: By design — custom bets are a feature for non-standard markets.

[S29] NaN combined odds display
  Severity: Suggestion
  Detail: If a bet has non-numeric odds somehow, the frontend multiply chain
  produces NaN. Schema validation should prevent this, but no frontend guard.
  Impact: Negligible — backend validates odds are numeric.

=== FRONTEND (11 findings) ===

[W30] Password reset: no client-side validation
  Severity: Warning
  Detail: The password reset form doesn't enforce minimum length or complexity
  on the client side. Backend validates, but user gets a generic error.
  Impact: UX issue — user doesn't know requirements until submit fails.

[W31] Remove pick: no confirmation dialog
  Severity: Warning
  Detail: Clicking "Remove Pick" on AccaDetail immediately deletes the bet
  without a confirmation prompt. Easy to accidentally delete.
  Impact: UX concern. Bet can be re-added if acca is still open.

[W32] Non-numeric URL parameters
  Severity: Warning
  Detail: groupId and accaId from useParams() are strings. parseInt() is used
  inconsistently. Non-numeric values cause failed API calls with unclear errors.
  Impact: Only affects users manually editing URLs. No crash, just poor UX.

[W33] Members list fetched but never displayed
  Severity: Warning
  Detail: GroupDetail fetches members and has removal logic but the members list
  isn't rendered in the JSX. Dead feature or incomplete implementation.
  Impact: Wasted API call. No security impact.

[S34] Join group input: no maxLength
  Severity: Suggestion
  Detail: The join-group input field doesn't have maxLength attribute. Frontend
  sanitizes to 6 chars before sending, but user can type unlimited chars.
  Impact: Cosmetic only — value is truncated before API call.

[W35] Non-awaited loadAccaDetails
  Severity: Warning
  Detail: In some handlers, loadAccaDetails() is called without await. The UI
  might not reflect the latest state when the function returns.
  Impact: Race condition that causes stale UI briefly. Self-resolves on next load.

[S36] structuredData object spread
  Severity: Suggestion
  Detail: Minor code quality — spreading objects that could be passed directly.
  Impact: No functional impact.

[S37] Same password allowed on change
  Severity: Suggestion
  Detail: Change-password allows setting the same password as the current one.
  Impact: Not a real issue — user's choice.

[W38] Delete acca: no double-submit protection
  Severity: Warning
  Detail: If an admin clicks "Delete Acca" and the API is slow, they could
  click again. No isSubmitting guard.
  Impact: Second click would fail (acca already deleted), just poor UX.

[S39] Bookmaker links fetched unauthenticated
  Severity: Suggestion
  Detail: getBookmakerLinks() is called before login check. The endpoint may
  not require auth, but it's a wasted call if user isn't logged in.
  Impact: One unnecessary API call on page load.

[W40] Stale acca status after lock
  Severity: Warning
  Detail: If user is viewing an open acca when it auto-locks (background task),
  the UI still shows "open" until page refresh. No polling or WebSocket update.
  Impact: User might try to add a pick and get an error. Not exploitable — backend
  enforces the lock.
